## 1. ภาพรวม

ตัวแก้ปัญหา (Solver) ของ MayWin จะสร้างตารางเวรพยาบาลรายเดือนสำหรับหน่วยงานในโรงพยาบาลโดยอัตโนมัติ โดยพิจารณาจากรายชื่อพยาบาล, ช่วงเวลาที่จัดตาราง (จำนวนวัน), ประเภทเวร และความต้องการบุคลากร เพื่อหาการจัดเวรที่:

1. **ครอบคลุมความต้องการบุคลากรทั้งหมด** (เป้าหมายหลัก)
2. **ลดค่าใช้จ่ายบุคลากร / ค่าล่วงเวลา (Overtime)** (เป้าหมายรอง)
3. **เคารพความต้องการของพยาบาล** (เป้าหมายลำดับที่สาม)
4. **กระจายภาระงานอย่างเป็นธรรม** (เป้าหมายลำดับที่สี่)

ตัวแก้ปัญหานี้ถูกพัฒนาขึ้นโดยใช้ **แบบจำลองความพึงพอใจในเงื่อนไข CP-SAT (CP-SAT constraint satisfaction model)** ซึ่งเป็นเอนจินการโปรแกรมจำนวนเต็มแบบ branch-and-bound ที่จะพิสูจน์หาคำตอบที่ดีที่สุด (Optimality) หรือส่งคืนคำตอบที่ดีที่สุดที่พบภายในเวลาที่กำหนด

## 2. สถาปัตยกรรมระบบ

```
NestJS Backend
     │
     ▼
SolverAdapter (solver.adapter.ts)
     │  แปลง NormalizedInput.v1 → SolveRequest JSON
     │  สร้างกระบวนการลูก (Child process)
     ▼
solver_cli.py  ──────── (Python / OR-Tools CP-SAT)
     │
     ├── Phase 1: build_solver_model(emergency_mode=False)
     │       ข้อกำหนดครอบคลุมแบบเคร่งครัด: จำนวนที่จัด = ความต้องการ
     │
     └── Phase 2: build_solver_model(emergency_mode=True)
             ข้อกำหนดครอบคลุมแบบยืดหยุ่น: จำนวนที่จัด + ส่วนที่ขาด >= ความต้องการ
             จะใช้เมื่อ Phase 1 ไม่สามารถหาคำตอบได้ (Infeasible)
```

TypeScript adapter (`solver.adapter.ts`) จะเขียนข้อมูลคำขอลงในไฟล์ JSON ชั่วคราว, รันคำสั่ง `solver_cli.py --cli --input <file> --output <file>`, อ่านผลลัพธ์กลับมา และลบไฟล์ชั่วคราวทิ้ง

### การตรวจจับชื่อเวร (Shift Name Detection)

ตัวแก้ปัญหาจะระบุประเภทเวรโดยการ **จับคู่ข้อความที่ตรงกันทุกประการ (Case-insensitive)** ในอาเรย์ของเวร:

| ค่าในอาเรย์ | ตรวจพบเป็น |
|---|---|
| `"morning"` | เวรเช้า — เปิดใช้งานข้อกำหนดเกี่ยวกับเลเบล |
| `"evening"` | เวรบ่าย/เย็น — เปิดใช้งานข้อกำหนดเกี่ยวกับเลเบล |
| `"night"` | เวรดึก — เปิดใช้งานข้อกำหนดเกี่ยวกับเลเบล |
| `"M"`, `"A"`, `"N"` | **ไม่ถูกตรวจพบ** — ข้อกำหนดที่ใช้เลเบลจะถูกปิดใช้งานโดยไม่แจ้งเตือน |

> [!WARNING]
> ปัจจุบันระบบในสภาพแวดล้อมจริง (Production) ส่งรหัสย่อ (`M`, `A`, `N`) ซึ่งหมายความว่าข้อกำหนดที่อิงตามชื่อเวรทั้งหมด (เช่น เพดานเวรดึก, ข้อห้ามเวรดึกต่อเช้า, การจำกัดประเภทเวร, บทลงโทษเวรบ่ายต่อดึก ฯลฯ) จะ **ไม่ทำงานใน Production** นี่เป็นปัญหาความไม่สอดคล้องที่ทราบกันดี

## 3. โครงสร้างข้อมูลนำเข้า (Input Schema)

```json
{
  "nurses":  ["N1", "N2", "N3"],
  "days":    ["2026-04-01", "2026-04-02", "..."],
  "shifts":  ["morning", "evening", "night"],
  "demand":  {
    "2026-04-01": { "morning": 2, "evening": 2, "night": 1 }
  },

  "availability":  { "N1": { "2026-04-01": { "morning": 0 } } },
  "preferences":   { "N1": { "2026-04-01": { "night": 5 } } },
  "nurse_skills":  { "N1": ["Senior"] },
  "required_skills": { "2026-04-01": { "morning": { "Senior": 1 } } },

  "backup_nurses":              ["N3"],
  "regular_shifts_per_nurse":   { "N1": 20 },
  "max_overtime_per_nurse":     { "N1": 8 },
  "min_total_shifts_per_nurse": { "N1": 15 },

  "rules":    { ... },
  "weights":  { ... },
  "goal_priority":    { "coverage": 1, "cost": 2, "preference": 3, "fairness": 4 },
  "fairness_weights": { "workload_balance": 1, "night_balance": 1, "shift_type_balance": 1 },

  "time_limit_sec":    20.0,
  "num_search_workers": 8,
  "random_seed":        null,
  "enable_cp_sat_log":  false
}
```

### ความพร้อม (Availability) เทียบกับ ความพึงพอใจ (Preferences)

| ฟิลด์ | ความหมาย | ผลกระทบ |
|---|---|---|
| `availability[n][d][s] = 0` | พยาบาล **ไม่สามารถ** ทำงานในช่วงนี้ได้ | บังคับอย่างเคร่งครัด — การมอบหมายถูกบังคับเป็น 0 |
| `availability[n][d][s] = 1` | พยาบาล **สามารถ** ทำงานได้ (ค่าเริ่มต้น) | ไม่มีผลต่อฟังก์ชันเป้าหมาย |
| `preferences[n][d][s] = P` | พยาบาล **ไม่ชอบ** ช่วงเวลานี้ (คะแนนบทลงโทษ P) | แบบยืดหยุ่น — เพิ่ม `P × weight` ในฟังก์ชันเป้าหมาย |

## 4. ระยะการประมวลผล (Solve Phases)

ตัวแก้ปัญหาใช้ **กลยุทธ์สองระยะ** เพื่อรับประกันว่าจะมีคำตอบส่งกลับมา แม้ว่าปัญหาจะไม่สามารถหาคำตอบได้ภายใต้กฎที่เคร่งครัด:

```
Phase 1 — โหมดเคร่งครัด (Strict Mode)
  ├── ความครอบคลุมต้องเป๊ะ (HARD): sum(x[n,d,s]) == demand[d][s]
  ├── บังคับใช้ข้อกำหนดเคร่งครัดทั้งหมด (ความพร้อม, เพดานล่วงเวลา, เพดานเวรดึก, …)
  └── หากได้ผลลัพธ์ที่ดีที่สุด (OPTIMAL) หรือหาคำตอบได้ (FEASIBLE) โดยไม่มีการขาดแคลนพยาบาล → เสร็จสิ้น ✓

Phase 2 — โหมดฉุกเฉิน (Emergency Mode) (ใช้เมื่อ Phase 1 ล้มเหลวเท่านั้น)
  ├── ความครอบคลุมเป็นแบบยืดหยุ่น (SOFT): sum(x[n,d,s]) + under[d,s] >= demand[d][s]
  ├── ส่วนที่ขาด (under[d,s]) จะถูกทำโทษหนักมากในฟังก์ชันเป้าหมาย (2,000,000 × priority_scale)
  ├── จำนวนเวรสูงสุดต่อวันอาจเพิ่มเป็น 2 (หากเปิดใช้งาน allow_second_shift_same_day_in_emergency)
  ├── เพดานเวรดึกรายสัปดาห์กลายเป็นแบบยืดหยุ่น (ใช้บทลงโทษแทนการบังคับ)
  ├── กฎชั่วโมงพักผ่อนกลายเป็นแบบยืดหยุ่น (ใช้บทลงโทษแทนการบังคับ)
  └── การจำกัดประเภทเวรกลายเป็นแบบยืดหยุ่น (ส่วนที่เกินจะถูกทำโทษ)

หาก Phase 2 ยังไม่สามารถหาคำตอบได้ (INFEASIBLE) → status = "INFEASIBLE"
```

### รหัสสถานะ (Status Codes)

| สถานะ | ความหมาย |
|---|---|
| `OPTIMAL` | Phase 1 แก้ปัญหาได้ และพิสูจน์แล้วว่าเป็นคำตอบที่ดีที่สุดในโลก |
| `FEASIBLE` | Phase 1 แก้ปัญหาได้ภายในเวลาที่กำหนด แต่ยังไม่พิสูจน์ว่าเป็นคำตอบที่ดีที่สุด |
| `EMERGENCY_OPTIMAL` | Phase 2 แก้ปัญหาได้ และพิสูจน์แล้วว่าดีที่สุด (อาจมีการขาดแคลนพยาบาล) |
| `EMERGENCY_FEASIBLE` | Phase 2 แก้ปัญหาได้ภายในเวลาที่กำหนด |
| `INFEASIBLE` | ล้มเหลวทั้งสองระยะ ไม่สามารถจัดตารางได้เลย |
| `ERROR` | เกิดข้อผิดพลาดหรือ CLI ค้าง |
| `TIMEOUT` | กระบวนการของ Solver ถูกหยุดเนื่องจากเกินกำหนดเวลาจริง |

## 5. ตัวแปรการตัดสินใจ (Decision Variables)

แบบจำลองสร้าง **ตัวแปรฐานสอง (Binary variable) หนึ่งตัวต่อชุด (พยาบาล, วัน, เวร)**:

```
x[n, d, s] ∈ {0, 1}
  1 = พยาบาล n ถูกมอบหมายให้เข้าเวร s ในวันที่ d
  0 = ไม่ถูกมอบหมาย
```

ตัวแปรสนับสนุนอื่นๆ:

| ตัวแปร | ประเภท | วัตถุประสงค์ |
|---|---|---|
| `over[n]` | IntVar ≥ 0 | จำนวนเวรล่วงเวลาสำหรับพยาบาล n |
| `under[d,s]` | IntVar ≥ 0 | จำนวนพยาบาลที่ขาดในช่อง (d, s) — เฉพาะ Phase 2 |
| `override[n,d,s]` | BoolVar | แฟล็กการยกเว้นกรณีฉุกเฉิน (ปัจจุบันเป็น 0 เสมอ — ความพร้อมจะเคร่งครัดเสมอ) |
| `extra_ot[n,d]` | BoolVar | 1 หากพยาบาล n ทำงานทั้งเวรเช้าและเวรบ่ายในวัน d |
| `ev_nt[n,d]` | BoolVar | 1 หากพยาบาล n ทำงานทั้งเวรบ่ายและเวรดึกในวัน d |

## 6. ข้อกำหนดที่ต้องปฏิบัติตามอย่างเคร่งครัด (Hard Constraints)

ข้อกำหนดแบบเคร่งครัดคือ **กฎที่ Solver ห้ามละเมิดเด็ดขาด** เมื่อสร้างตาราง หากมีกฎข้อใดข้อหนึ่งไม่สามารถทำได้ Solver จะยกระดับเป็น **โหมดฉุกเฉิน** (Phase 2) ซึ่งจะพยายามอย่างเต็มที่แต่จะแจ้งเตือนว่ามีการขาดแคลนพยาบาล กฎเหล่านี้คือมาตรฐานขั้นต่ำที่ทุกตารางต้องปฏิบัติตาม

---

### 6.1 — ทุกช่วงเวรต้องมีคนทำงาน (Coverage)

**ความหมาย:** ตารางต้องมีจำนวนพยาบาลตรงตามที่กำหนดในทุกเวร ทุกวัน ห้ามปล่อยให้เวรใดว่าง

**ตัวอย่าง:**
> หน่วยงานต้องการ **พยาบาล 5 คนในเวรเช้า, 5 คนในเวรบ่าย และ 4 คนในเวรดึก** ทุกวันธรรมดา  
> ในวันหยุด จำนวนลดลง 1 คน: **เช้า 4, บ่าย 4, ดึก 3**  
>
> Solver *ต้อง* หาพยาบาลมาเติมให้เต็มทุกช่องสำหรับทุกวันในเดือนนั้น — หากวันธรรมดาเวรเช้ามีพยาบาลเพียง 4 คน จะถือว่าเป็นการละเมิดกฎ

**จะเกิดอะไรขึ้นถ้าทำไม่ได้?** หากไม่มีพยาบาลเพียงพอที่จะเติมให้เต็มทุกช่อง (เช่น พยาบาลลางานพร้อมกันมากเกินไป) Solver จะเข้าสู่ **โหมดฉุกเฉิน** ในโหมดนี้ การเติมคนให้เต็มจะเป็นเป้าหมายแบบยืดหยุ่นที่มีบทลงโทษมหาศาล — Solver จะยังคงพยายามเติมให้เต็ม แต่จะรายงานว่าช่องใดที่คนไม่พอแทนที่จะหยุดทำงาน

---

### 6.2 — ต้องเคารพความพร้อมของพยาบาล (Availability)

**ความหมาย:** หากพยาบาลทำเครื่องหมายว่าไม่ว่างในวันหรือเวรใด (เช่น ลาพักร้อน, ลาป่วย หรือวันหยุดที่อนุมัติแล้ว) Solver จะ **ไม่มีทาง** มอบหมายเวรให้พยาบาลคนนั้นในช่วงเวลาดังกล่าว กฎนี้จะไม่ถูกยกเว้นแม้ในโหมดฉุกเฉิน

**ตัวอย่าง:**
> พยาบาล A ยื่นลากิจในวันที่ 15 เมษายน  
> ต่อให้เวรดึกวันที่ 15 เมษายนจะขาดคนอย่างหนัก Solver ก็จะไม่จัดตารางให้พยาบาล A  
> แต่จะรายงานว่า "ขาดพยาบาล 1 คนในเวรดึก วันที่ 15 เมษายน" ในรายการคนไม่พอแทน

**หมายเหตุ:** ความพร้อมที่ระบุเป็น `PREFERRED` หมายถึงพยาบาล *สามารถ* ทำงานในเวรนั้นได้ — ไม่ได้เป็นการห้ามไม่ให้จัดตารางในเวรอื่นของวันเดียวกัน เว้นแต่จะมีการระบุ `UNAVAILABLE` ในเวรอื่นๆ เหล่านั้นอย่างชัดเจน

---

### 6.3 — พยาบาลหนึ่งคนทำได้หนึ่งเวรต่อวัน (Daily Shift Limit)

**ความหมาย:** โดยค่าเริ่มต้น พยาบาลทำงานได้เพียง **หนึ่งเวรต่อวัน** — ไม่สามารถรับเวรเช้า *และ* เวรดึกในวันปฏิทินเดียวกันได้

**ตัวอย่าง:**
> พยาบาล B ถูกมอบหมายให้เข้าเวรเช้าวันที่ 3 พฤษภาคมแล้ว  
> Solver จะไม่สามารถมอบหมายให้พยาบาล B เข้าเวรบ่ายหรือเวรดึกในวันที่ 3 พฤษภาคมได้อีก

**ข้อยกเว้นในกรณีฉุกเฉิน:** หากหน่วยงานขาดแคลนคนอย่างวิกฤตและเปิดใช้งาน `allow_second_shift_same_day_in_emergency` Solver *อาจ* มอบหมายให้พยาบาลคนเดียวทำ 2 เวรในวันเดียวกันเป็นทางเลือกสุดท้าย — แต่จะมีการลงโทษหนักและระบุไว้อย่างชัดเจนในผลลัพธ์

---

### 6.4 — การทำงานล่วงเวลาต้องไม่เกินงบประมาณ (Overtime Cap)

**ความหมาย:** พยาบาลแต่ละคนมี **โควตาปกติ** ในการเข้าเวรต่อเดือน (เช่น 20 เวร) เวรที่เกินจากนั้นจะนับเป็นงานล่วงเวลา (Overtime) จำนวนเวรล่วงเวลาทั้งหมดของพยาบาลคนใดคนหนึ่งต้องไม่เกินค่าสูงสุดที่กำหนด (ค่าเริ่มต้น: **12 เวรล่วงเวลา** ต่อเดือน)

**ตัวอย่าง:**
> โควตาปกติของพยาบาล C คือ 20 เวร  
> Solver สามารถมอบหมายให้เธอเข้าเวรได้สูงสุด 32 เวร (ปกติ 20 + ล่วงเวลา 12)  
> การมอบหมายเวรที่ 33 จะเป็นการละเมิดกฎนี้

**เพิ่มเติม:** หากพยาบาลเข้าเวรทั้ง **เช้าและบ่ายในวันเดียวกัน** เวรที่สองจะถูกนับเป็นเวรล่วงเวลา 1 เวรโดยอัตโนมัติ — แม้ว่าจำนวนเวรทั้งหมดจะยังอยู่ในโควตาปกติก็ตาม

---

### 6.5 — พยาบาลทุกคนต้องทำงานขั้นต่ำตามที่กำหนด (Minimum Shifts)

**ความหมาย:** เพื่อให้แน่ใจว่าไม่มีพยาบาลคนใดถูกปล่อยว่างตลอดทั้งเดือน (เช่น พนักงานพาร์ทไทม์ที่มีสัญญาจ้างขั้นต่ำ) พยาบาลแต่ละคนต้องได้รับมอบหมายเวร *อย่างน้อย* ตามจำนวนที่กำหนดไว้

**ตัวอย่าง:**
> พยาบาลพาร์ทไทม์มีสัญญาจ้างขั้นต่ำ **10 เวรต่อเดือน**  
> Solver ต้องจัดเวรให้เธออย่างน้อย 10 เวร — ไม่สามารถให้เพียง 7 เวรได้ แม้ว่าจะจัดคนลงเวรครบตามความต้องการแล้วก็ตาม

---

### 6.6 — ห้ามต่อเวรเช้าทันทีหลังจากเวรดึก (Night → Morning)

**ความหมาย:** หากพยาบาลเพิ่งออกเวรดึก (ซึ่งเลิกตอน 06:00) เธอจะไม่สามารถเริ่มเวรเช้าในวันถัดไปได้ทันที (ซึ่งเริ่ม 06:00 ในเช้าวันที่เธอเพิ่งเลิกงาน) เพราะจะไม่มีเวลาพักผ่อนเลย

**ตัวอย่าง:**
> พยาบาล D ทำงานเวรดึกวันอังคาร (22:00 วันอังคาร → 06:00 วันพุธ)  
> เธอ **ไม่สามารถ** ถูกมอบหมายเวรเช้าวันพุธ (06:00–14:00) ได้  
> อย่างไรก็ตาม เธอสามารถทำงานเวรบ่ายวันพุธ (14:00–22:00) ได้ — ซึ่งจะทำให้มีเวลาพัก 8 ชั่วโมง

> [!IMPORTANT]
> กฎนี้ถูก **เปิดใช้งานโดยค่าเริ่มต้น** และเป็นหนึ่งในกฎความปลอดภัยที่สำคัญที่สุดของระบบ หากปิดใช้งานจะมีความเสี่ยงที่จะจัดเวรให้พยาบาลทำงานต่อเนื่องกันโดยไม่ได้พัก

---

### 6.7 — ห้ามทำงานทั้งเวรเช้าและเวรดึกในวันเดียวกัน (Morning → Night, ทางเลือก)

**ความหมาย:** พยาบาลไม่สามารถถูกมอบหมายให้ทำเวรเช้า *และ* เวรดึกในวันปฏิทินเดียวกัน — เพราะจะเป็นการทำงานต่อเนื่อง 16 ชั่วโมงโดยมีเวลาพักเพียง 2 ชั่วโมง

**ตัวอย่าง:**
> พยาบาล E เข้าเวรเช้าวันจันทร์ (06:00–14:00)  
> เธอ **ไม่สามารถ** ถูกมอบหมายเวรดึกวันจันทร์ (22:00–06:00) ได้อีก

**สถานะค่าเริ่มต้น:** กฎนี้ถูก **ปิดไว้โดยค่าเริ่มต้น** (Solver จะห้ามเฉพาะกรณีต่อเนื่องในข้อ 6.6 เท่านั้น) สามารถเปิดใช้งานได้โดยตั้งค่า `forbid_morning_to_night_same_day = true` หากนโยบายหน่วยงานของคุณต้องการ

---

### 6.8 — ทำเวรดึกไม่เกิน 2 ครั้งต่อสัปดาห์ (Weekly Night Cap)

**ความหมาย:** ในสัปดาห์ใดๆ (7 วัน) พยาบาลสามารถทำงานเวรดึกได้สูงสุด **2 ครั้ง** (ปรับเปลี่ยนได้) เนื่องจากเวรดึกส่งผลกระทบต่อร่างกายมากกว่า การจำกัดจำนวนจึงช่วยลดความเหนื่อยล้า

**ตัวอย่าง:**
> ในสัปดาห์ที่ 7–13 เมษายน พยาบาล F เข้าเวรดึกวันจันทร์และวันพฤหัสบดี  
> Solver จะไม่มอบหมายเวรดึกครั้งที่สามให้เธอในสัปดาห์นั้นอีก — เช่น เวรดึกวันศุกร์จะเป็นช่วงเวลาที่เธอทำไม่ได้

**ในโหมดฉุกเฉิน:** กฎนี้จะกลายเป็นแบบยืดหยุ่น — Solver สามารถจัดเวรดึกเกิน 2 ครั้งต่อสัปดาห์ได้ แต่จะมีการลงโทษหนักสำหรับเวรที่เกินมา

---

### 6.9 — ต้องมีวันหยุดอย่างน้อย 2 วันต่อสัปดาห์ (Weekly Days Off)

**ความหมาย:** พยาบาลทุกคนต้องมี **วันหยุดเต็มวันอย่างน้อย 2 วัน** ในแต่ละสัปดาห์ (7 วัน) "วันหยุด" หมายถึงการไม่ถูกมอบหมายให้เข้าเวรใดๆ เลยในวันนั้น

**ตัวอย่าง:**
> ในสัปดาห์ที่ 14–20 เมษายน พยาบาลทำงานวันจันทร์ถึงวันศุกร์ — นั่นคือทำงาน 5 วัน  
> Solver จะดูแลให้เธอมี **วันหยุดอย่างน้อย 2 วัน** ดังนั้นวันเสาร์และวันอาทิตย์จะเป็นวันว่างของเธอ  
>
> หากช่วงเวลาที่จัดตารางสั้นกว่า (เช่น จัดแค่ 5 วัน) เพดานนี้จะปรับตามสัดส่วน

---

### 6.10 — ต้องมีวันหยุดอย่างน้อย 11 วันต่อเดือน (Monthly Days Off)

**ความหมาย:** ตลอดทั้งเดือน (ปกติ 30 วัน) พยาบาลแต่ละคนต้องมี **วันหยุดรวมอย่างน้อย 11 วัน** — หมายความว่าเธอสามารถทำงานได้สูงสุด **19 วัน** ในหนึ่งเดือน

**ตัวอย่าง:**
> เดือนเมษายนมี 30 วัน  
> พยาบาล G สามารถถูกมอบหมายวันทำงานได้สูงสุด **19 วัน** (30 − 11 = 19)  
> ไม่ว่าความต้องการพยาบาลจะเร่งด่วนเพียงใด Solver จะไม่จัดตารางให้เธอเป็นวันที่ 20

> [!IMPORTANT]
> นี่คือหนึ่งในกฎหลักที่จำกัดขีดความสามารถ หากมีพยาบาล 6 คน × ทำงานได้สูงสุดคนละ 19 วัน = 114 คน-วัน หากความต้องการรวมสูงกว่านั้น ตารางจะขาดคนทันทีแม้จะยังไม่ได้พิจารณาเรื่องการทำงานล่วงเวลาก็ตาม

---

### 6.11 — ทำงานติดต่อกันได้ไม่เกิน N วัน (Consecutive Work Days, ทางเลือก)

**ความหมาย:** พยาบาลไม่สามารถถูกจัดตารางให้ทำงานติดต่อกันเกินจำนวนวันที่กำหนดโดยไม่มีวันหยุดคั่น เพื่อป้องกันความเหนื่อยล้าจากการทำงานยาวนานต่อเนื่อง

**ตัวอย่าง (หากตั้งไว้ที่ 5 วัน):**
> พยาบาล H ทำงานวันจันทร์ถึงวันศุกร์ — ครบ 5 วันติดต่อกัน  
> เธอ **ต้อง** มีวันหยุดอย่างน้อยหนึ่งวันในวันเสาร์หรือวันอาทิตย์ ก่อนที่จะทำงานได้อีกครั้งในวันจันทร์  
> Solver จะไม่อนุญาตให้ทำงาน จันทร์–อังคาร–พุธ–พฤหัส–ศุกร์–เสาร์ (6 วันรวด)

**สถานะค่าเริ่มต้น:** **ปิดใช้งาน** โดยค่าเริ่มต้น (`null`) เปิดใช้งานได้โดยตั้งค่า `max_consecutive_work_days` เป็นตัวเลขในโปรไฟล์ข้อกำหนด (Constraint Profile)

---

### 6.12 — ทำเวรดึกติดต่อกันได้ไม่เกิน 3 ครั้ง (Consecutive Nights)

**ความหมาย:** พยาบาลไม่สามารถถูกจัดตารางให้ทำเวรดึกติดต่อกันเกิน **3 ครั้ง** การทำงานเวรดึก 4 ครั้งขึ้นไปติดต่อกันส่งผลเสียต่อการนอนหลับอย่างรุนแรงและถือว่าไม่ปลอดภัย

**ตัวอย่าง:**
> พยาบาล I เข้าเวรดึกวันจันทร์ อังคาร และพุธ  
> Solver จะ **ไม่** มอบหมายเวรดึกวันพฤหัสให้เธออีก — เธอต้องได้เวรอื่นที่ไม่ใช่เวรดึก (หรือวันหยุด) ก่อนที่จะได้รับเวรดึกอีกครั้ง

---

### 6.13 — ทำงานติดต่อกันห้ามเกิน N เวรตลอดระยะเวลา (Consecutive Shifts, ทางเลือก)

**ความหมาย:** นี่คือกฎที่เข้มงวดกว่าข้อ 6.11 แทนที่จะนับเป็น *วันทำงาน* กฎนี้จะนับแยกเป็นแต่ละ **ช่องเวร** ที่ติดกัน — โดยมองตารางเป็นลำดับยาว: จันทร์-เช้า → จันทร์-บ่าย → จันทร์-ดึก → อังคาร-เช้า → ...

**ตัวอย่าง (หากตั้งไว้ที่ 3):**
> พยาบาล J ทำงาน จันทร์-เช้า, จันทร์-บ่าย, จันทร์-ดึก นี่คือ 3 เวรติดต่อกัน — ถึงขีดจำกัดแล้ว  
> Solver จะไม่มอบหมาย อังคาร-เช้า ให้เธอ (เพราะจะเป็นเวรที่ 4 ติดต่อกัน)

**สถานะค่าเริ่มต้น:** **ปิดใช้งาน** โดยค่าเริ่มต้น (`null`) ไม่ค่อยได้ใช้งาน ส่วนใหญ่จะพึ่งพากฎ 6.11 และ 6.12 แทน

---

### 6.14 — ชั่วโมงพักขั้นต่ำระหว่างเวรที่ติดต่อกัน (Rest Hours, ทางเลือก)

**ความหมาย:** Solver จะตรวจสอบเวลาจริงของเวรที่อยู่ติดกัน หากช่วงว่างระหว่างเวลาเลิกของเวรหนึ่งกับเวลาเริ่มของเวรถัดไปสั้นกว่าชั่วโมงพักขั้นต่ำที่กำหนด จะไม่อนุญาตให้จัดเวรคู่นั้น

**ตารางเวลาเวรที่ใช้:**
| เวร | เริ่ม | เลิก |
|---|---|---|
| เช้า (Morning) | 06:00 | 14:00 |
| บ่าย/เย็น (Afternoon/Evening) | 14:00 | 22:00 |
| ดึก (Night) | 22:00 | 06:00 (วันถัดไป) |

**ตัวอย่าง (หากพักขั้นต่ำ = 11 ชั่วโมง):**
> พยาบาล K เลิก **เวรบ่าย** ตอน 22:00 วันจันทร์  
> เธอไม่สามารถเริ่ม **เวรเช้า** ตอน 06:00 วันอังคารได้ — เพราะมีเวลาพักเพียง 8 ชั่วโมง ซึ่งต่ำกว่าขั้นต่ำ 11 ชั่วโมง  
> แต่เธอ *สามารถ* เริ่มเวรบ่ายตอน 14:00 วันอังคารได้ (มีเวลาพัก 16 ชั่วโมง ✓)

**ในโหมดฉุกเฉิน:** กฎนี้จะกลายเป็นแบบยืดหยุ่น — การละเมิดจะถูกทำโทษแต่ยอมให้เกิดขึ้นได้หากเป็นทางเลือกสุดท้าย

**สถานะค่าเริ่มต้น:** **ปิดใช้งาน** โดยค่าเริ่มต้น (`null`) เปิดใช้งานโดยตั้งค่า `min_rest_hours_between_shifts`

---

### 6.15 — พยาบาลห้ามทำเวรประเภทเดิมซ้ำกันมากเกินไปต่อเดือน (Shift-Type Limits)

**ความหมาย:** เพื่อป้องกันไม่ให้พยาบาลคนเดิมต้องทำแต่เวรดึกทั้งเดือน จึงมีการจำกัดจำนวนครั้งสูงสุดในแต่ละประเภทเวร ค่าเริ่มต้นคือ **9 ครั้งต่อประเภท** (ดังนั้นในหนึ่งเดือน พยาบาลหนึ่งคนจะทำเวรเช้าได้ไม่เกิน 9 ครั้ง, บ่าย 9 ครั้ง และดึก 9 ครั้ง)

**ตัวอย่าง:**
> ถึงกลางเดือนเมษายน พยาบาล L ทำเวรเช้าไปแล้ว 9 ครั้ง  
> แม้ว่าในสัปดาห์สุดท้ายของเมษายน เวรเช้าจะขาดคนอย่างหนัก Solver ก็จะไม่มอบหมายเวรเช้าให้เธออีก  
> แต่เธอยังสามารถรับเวรบ่ายหรือเวรดึกได้ หากยังไม่เกินโควตาเหล่านั้น

**ข้อยกเว้น:** สามารถระบุรายชื่อพยาบาลใน `shift_type_limit_exempt_nurses` เพื่อยกเว้นกฎนี้ได้ (เช่น ผู้เชี่ยวชาญที่ทำงานเฉพาะเวรเช้าเท่านั้น)

**ในโหมดฉุกเฉิน:** Solver อาจจัดให้เกินเพดานได้ แต่จะลงโทษสำหรับทุกเวรที่เกินมา

---

### 6.16 — เวรที่ต้องใช้ทักษะเฉพาะต้องมีพยาบาลที่มีคุณสมบัติเหมาะสม (Skill Requirements)

**ความหมาย:** บางเวรต้องการพยาบาลอย่างน้อยหนึ่งคนที่มีคุณสมบัติเฉพาะ — เช่น ทุกเวรเช้าต้องมีพยาบาลระดับอาวุโส (Senior) อย่างน้อย 1 คนอยู่หน้างาน Solver จะมอบหมายเฉพาะพยาบาลที่มีแท็ก/ทักษะ (Tag/Skill) ตามที่ต้องการเพื่อให้ครบตำแหน่งเหล่านั้น

**ตัวอย่าง:**
> แผนก ICU ต้องการ **พยาบาล Senior 1 คนในทุกเวร ทุกวัน**  
> หน่วยงานมีพยาบาลทั้งหมด 8 คน แต่มีเพียง 3 คนที่มีแท็ก `"Senior"`  
> Solver จะต้องใส่พยาบาลหนึ่งในสามคนนี้ลงในทุกเวรเสมอ — โดยไม่คำนึงถึงความพึงพอใจหรือภาระงานของพวกเขา — เพราะข้อกำหนดด้านทักษะเป็นข้อกำหนดแบบเคร่งครัด  
> หากพยาบาล Senior ทั้ง 3 คนไม่ว่างในวันใดวันหนึ่ง Solver จะรายงานว่าเวรนั้นขาดคน

## 7. ข้อกำหนดแบบยืดหยุ่นและฟังก์ชันเป้าหมาย (Soft Constraints & Objective Function)

Solver จะ **พยายามทำให้ค่าต่ำสุด (Minimize)** ของผลรวมถ่วงน้ำหนักของบทลงโทษ ข้อกำหนดแบบยืดหยุ่นทั้งหมดจะปรากฏเป็นพจน์ต่างๆ ในฟังก์ชันเป้าหมายนี้

```
Minimize (ทำให้เหลือน้อยที่สุด):
  บทลงโทษความครอบคลุม (coverage_penalty)          (ช่องที่ขาดพยาบาล)
  + บทลงโทษการทำงานล่วงเวลา (overtime_penalty)        (จำนวนเวรล่วงเวลารวม)
  + บทลงโทษความสมดุลล่วงเวลา (overtime_balance_penalty) (กระจายงานล่วงเวลาให้เป็นธรรม)
  + บทลงโทษความพึงพอใจ (preference_penalty)      (การละเมิดความต้องการพยาบาล)
  + ความสมดุลภาระงาน (workload_balance)        (ความต่างระหว่างเวรรวมสูงสุด − ต่ำสุด)
  + ความสมดุลเวรดึก (night_balance)           (ความต่างระหว่างเวรดึกสูงสุด − ต่ำสุด)
  + ความสมดุลประเภทเวร (shift_type_balance)      (ความต่างระหว่างประเภทเวรสูงสุด − ต่ำสุดต่อคน)
  + บทลงโทษพยาบาลสำรอง (backup_nurse_penalty)    (ต้นทุนการใช้พยาบาลสำรอง/ภายนอก)
  + บทลงโทษเวรบ่ายต่อดึก (evening_to_night_penalty) (ทำงานทั้งบ่ายและดึกในวันเดียวกัน)
  + เวรที่สองในวันเดียวกัน (same_day_second_shift)   (การทำควบสองเวรในกรณีฉุกเฉิน)
  + การยกเว้นกฎฉุกเฉิน (emergency_override)      (มีการยกเว้นกฎกรณีฉุกเฉินใดๆ)
  + เวรที่เกินเพดานประเภท (shift_type_excess)       (เกินเพดานประเภทเวรในกรณีฉุกเฉิน)
```

### 7.1 บทลงโทษความครอบคลุม (เฉพาะ Phase 2)

```
priority_scale[coverage] × understaff_penalty × under[d,s]
```
นี่คือพจน์ที่มี **ความสำคัญสูงสุด** ด้วยค่า `priority_scale[coverage] = 10,000,000` และ `understaff_penalty = 2,000,000` การปล่อยให้คนขาดจึงมี "ราคา" ที่แพงมหาศาล

### 7.2 บทลงโทษการทำงานล่วงเวลา

```
overtime_penalty × over[n]   สำหรับทุก n
```
ลงโทษทุกๆ เวรล่วงเวลา ค่าน้ำหนักเริ่มต้น: 20

### 7.3 บทลงโทษความพึงพอใจ

```
priority_scale[preference] × preference_penalty_multiplier × p × x[n,d,s]
```
โดยที่ `p = preferences[n][d][s]` คือคะแนนความไม่ชอบของพยาบาลต่อช่วงเวลานั้น ยิ่ง `p` สูง = ยิ่งไม่ชอบมาก

### 7.4 เวรบ่ายต่อเวรดึกในวันเดียวกัน (บทลงโทษสูง)

```
evening_to_night_penalty × ev_nt[n,d]
```
ลงโทษการจัดเวรให้พยาบาลทำทั้งเวรบ่ายและเวรดึกในวันเดียวกัน ค่าน้ำหนักเริ่มต้น: **10,000** — แพงเกือบเท่าการปล่อยให้คนขาด ทำให้กฎนี้มีผลเกือบเท่ากฎเคร่งครัด

### 7.5 บทลงโทษพยาบาลสำรอง

```
50,000 × x[n,d,s]   สำหรับทุก n ใน backup_nurses, d, s
```
ทำให้ Solver เลือกใช้พยาบาลประจำก่อนพยาบาลสำรองหรือพยาบาลภายนอกอย่างชัดเจน

### 7.6 การทำควบสองเวรในวันเดียวกันกรณีฉุกเฉิน

```
same_day_second_shift_penalty × extra_same_day[n,d]
```
ในโหมดฉุกเฉิน จะลงโทษการจัดควบสองเวรต่อพยาบาลต่อวัน ค่าน้ำหนักเริ่มต้น: 150

## 8. ค่าน้ำหนักบทลงโทษ (Penalty Weights)

น้ำหนักทั้งหมดสามารถกำหนดค่าได้ในออบเจ็กต์ `weights` ของคำขอ

| ฟิลด์ | ค่าเริ่มต้น | คำอธิบาย |
|---|---|---|
| `understaff_penalty` | 2,000,000 | ต้นทุนต่อพยาบาลที่ขาดในหนึ่งช่องเวร (Phase 2) |
| `overtime_penalty` | 20 | ต้นทุนต่อเวรล่วงเวลา 1 เวร |
| `preference_penalty_multiplier` | 1 | ตัวคูณคะแนนความไม่ชอบของพยาบาล |
| `workload_balance_weight` | 0 | น้ำหนักในการเกลี่ยภาระงานให้เท่ากัน (ปิดไว้เป็นค่าเริ่มต้น) |
| `emergency_override_penalty` | 500 | ต้นทุนต่อการยกเว้นกฎเคร่งครัดหนึ่งครั้ง |
| `same_day_second_shift_penalty` | 150 | ต้นทุนต่อการควบสองเวรในกรณีฉุกเฉิน |
| `weekly_night_over_penalty` | 120 | ต้นทุนต่อเวรดึกที่เกินเพดานรายสัปดาห์ |
| `evening_to_night_penalty` | 10,000 | ต้นทุนสำหรับการทำเวรบ่าย + เวรดึกในวันเดียวกัน |
| `shift_type_balance_penalty` | 100 | ต้นทุนสำหรับความไม่สมดุลของประเภทเวรต่อพยาบาล |
| `overtime_balance_penalty` | 1,000 | ต้นทุนสำหรับความไม่สมดุลของงานล่วงเวลาระหว่างพยาบาล |

## 9. ลำดับความสำคัญของเป้าหมาย (Goal Priorities)

เป้าหมายถูกจัดลำดับตามความสำคัญ (1 = สูงสุด) แต่ละลำดับจะถูกแปลงเป็น **ตัวคูณสเกล (Scale multiplier)**:

| อันดับความสำคัญ | ตัวคูณสเกล |
|---|---|
| 1 | 10,000,000 |
| 2 | 10,000 |
| 3 | 1,000 |
| 4 | 100 |

ลำดับความสำคัญเริ่มต้น:

| เป้าหมาย | ความสำคัญเริ่มต้น |
|---|---|
| `coverage` (ความครอบคลุม) | **1** (สำคัญที่สุด) |
| `cost` (ต้นทุน) | 2 |
| `preference` (ความพึงพอใจ) | 3 |
| `fairness` (ความเป็นธรรม) | 4 |

ตัวคูณสเกลเหล่านี้ช่วยให้มั่นใจว่าเป้าหมายที่มีความสำคัญสูงกว่าจะมีผลเหนือฟังก์ชันเป้าหมายเสมอ แม้ว่าบทลงโทษของเป้าหมายที่สำคัญน้อยกว่าจะมีค่าสัมประสิทธิ์ที่มากก็ตาม

## 10. ระบบความเป็นธรรม (Fairness System)

มีการติดตามและลงโทษตัวชี้วัดความเป็นธรรม 3 ด้าน:

### ความสมดุลภาระงาน (Workload Balance)

```
workload_balance = จำนวนเวรรวมสูงสุด - จำนวนเวรรวมต่ำสุด   (ในกลุ่มพยาบาลทั้งหมด)
penalty = priority_scale[fairness] × fairness_weights.workload_balance × workload_balance
```

### ความสมดุลเวรดึก (Night Shift Balance)

```
night_balance = จำนวนเวรดึกสูงสุด - จำนวนเวรดึกต่ำสุด   (ในกลุ่มพยาบาลทั้งหมด)
penalty = priority_scale[fairness] × fairness_weights.night_balance × night_balance
```

### ความสมดุลประเภทเวร (ต่อคน) (Shift-Type Balance)

```
shift_balance[n] = max(เช้า, บ่าย, ดึก) - min(เช้า, บ่าย, ดึก)
penalty = shift_type_balance_penalty × priority_scale[fairness] × fairness_weights.shift_type_balance × shift_balance[n]
```

ตัวชี้วัดรายบุคคลนี้ช่วยลดการจัดให้พยาบาลคนใดคนหนึ่งต้องทำเวรประเภทเดียวซ้ำๆ มากเกินไป

### ความสมดุลงานล่วงเวลา (Overtime Balance)

```
overtime_balance = งานล่วงเวลาสูงสุด - งานล่วงเวลาต่ำสุด   (ในกลุ่มพยาบาลทั้งหมด)
penalty = overtime_balance_penalty × priority_scale[fairness] × overtime_balance
```

## 11. คะแนนความพึงพอใจของพยาบาล (Nurse Satisfaction Score)

หลังจากจัดตารางเสร็จ พยาบาลแต่ละคนจะได้รับคะแนนความพึงพอใจตั้งแต่ **1 ถึง 100**:

```
คะแนนเริ่มที่ = 100
  − (เวรที่ไม่ชอบ / เวรทั้งหมด) × 40    # ลดสูงสุด −40 สำหรับการละเมิดความพึงพอใจ
  − (เวรดึก / เวรทั้งหมด) × 20        # ลดสูงสุด −20 สำหรับสัดส่วนเวรดึกที่สูง
  − min(30, จำนวนเวรล่วงเวลา × 5)     # ลดสูงสุด −30 สำหรับงานล่วงเวลา
  − min(30, จำนวนการยกเว้นกฎฉุกเฉิน × 10) # ลดสูงสุด −30 สำหรับกรณีฉุกเฉิน
```

คะแนนสุดท้ายจะถูกจำกัดให้อยู่ในช่วง `[1, 100]`

## 13. การคำนวณขีดความสามารถ (Capacity Math)

ภายใต้ **กฎค่าเริ่มต้น** สำหรับเดือนที่มี 30 วัน:

| ข้อกำหนด | ขีดจำกัด |
|---|---|
| `min_total_days_off = 11` (วันหยุดขั้นต่ำ) | ทำงานได้สูงสุด 19 วัน |
| `max_shifts_per_day = 1` (เวรสูงสุดต่อวัน) | ทำงานได้สูงสุด 19 เวร/เดือน (Phase 1) |
| `max_shifts_per_day = 2` (กรณีฉุกเฉิน) | ทำงานได้สูงสุด 38 เวร/เดือน (Phase 2) |
| `max_overtime_per_nurse = 12` | ขีดจำกัดบน: ปกติ + 12 |

**ตัวอย่างความต้องการบุคลากร:** เช้า 3 + บ่าย 3 + ดึก 2 = **8 ช่อง/วัน × 30 วัน = 240 ช่อง/เดือน**

| จำนวนพยาบาล | ขีดความสามารถสูงสุด (Phase 2) | เป็นไปได้ไหม? |
|---|---|---|
| 6 | 6 × 38 = 228 | ❌ ขาด 12 เวร |
| 7 | 7 × 38 = 266 | ✅ เพียงพอ |
| 8 | 8 × 38 = 304 | ✅ สบายๆ |

## 14. ข้อจำกัดที่ทราบ

| ปัญหา | ผลกระทบ | วิธีแก้ไขเบื้องต้น |
|---|---|---|
| ระบบ Production ส่งรหัสเวรย่อ (`M`, `A`, `N`) | เพดานเวรดึก, การจำกัดประเภทเวร, กฎดึกต่อเช้า, บทลงโทษบ่ายต่อดึก ทั้งหมดจะไม่ทำงานโดยไม่แจ้งเตือน | เปลี่ยนชื่อเวรเป็น `"morning"`, `"evening"`, `"night"` ในส่วนของ Normalizer |
| ความพร้อม (Availability) เคร่งครัดเสมอ | ไม่สามารถสั่งพยาบาลที่ลงวันหยุดไว้ให้มาทำงานได้แม้ในกรณีฉุกเฉินขั้นสุด | ปัจจุบันยังไม่จำเป็น — เป็นไปตามการออกแบบ |
| `max_consecutive_work_days` และ `max_consecutive_shifts` เป็น `null` โดยค่าเริ่มต้น | ข้อกำหนดแบบช่วงเวลาต่อเนื่องจะไม่ทำงานเว้นแต่จะตั้งค่าไว้ชัดเจน | กำหนดค่าใน `ConstraintProfile` |
| ข้อกำหนดทักษะ Senior ตรวจสอบเฉพาะแท็ก `"Senior"` เท่านั้น | ทักษะจำเป็นอื่นๆ จะถูกละเลย | ขยายตรรกะ `required_skills` สำหรับประเภททักษะใหม่ๆ |
| กำหนดเวลาของ Solver เป็นเวลาจริง (Wall-clock) | กรณีที่มีพยาบาลจำนวนมากอาจส่งคืนแค่ `FEASIBLE` (ยังไม่พิสูจน์ว่าดีที่สุด) | เพิ่ม `time_limit_sec` หรือลด `num_search_workers` |
